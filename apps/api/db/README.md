# Senko API PostgreSQL schema

The Senko API uses Railway managed PostgreSQL as the future system of record for customer identity and administrative
history. The canonical Drizzle schema is [`src/db/schema.ts`](../src/db/schema.ts), and generated SQL migrations live in
[`db/migrations`](migrations).

The initial migration defines:

- `users`
- `accounts`
- `teams`
- `account_memberships`
- `team_memberships`
- `api_keys`
- `api_key_scopes`
- `admin_audit_events`

Production and development/test databases are separate Railway Postgres services in the same Railway project and
environment. Both are currently in Singapore and use Railway serverless mode. The exact service IDs are operational
configuration documented in the repository's `AGENTS.md`; they are not duplicated in public runtime configuration.

## Generate and check migrations

From the repository root:

```sh
pnpm --filter @senkocode/api db:generate
pnpm --filter @senkocode/api db:check
```

`db:generate` updates generated migration artifacts from the typed schema. `db:check` validates the migration journal
without connecting to Railway. The API build runs `db:check` before the Wrangler dry-run.

There is deliberately no `db:migrate` script yet. Applying a migration changes an external database and requires an
explicit target and approval. Development and test work must target the development/test Railway Postgres service;
production migration is a separate release operation.

## Security boundary

- UUIDs are generated by PostgreSQL's built-in `gen_random_uuid()`.
- API key rows store a non-secret public lookup ID, a display prefix, a versioned 64-character hash, and lifecycle
  metadata. They never store the raw key.
- The initial scopes are `models:read`, `inference:chat`, and `inference:responses`.
- Composite foreign keys prevent teams, memberships, key creators, rotations, scopes, and audit actors from crossing
  account boundaries.
- Administrative audit metadata must be a JSON object. Application code must enforce a content-free allowlist before
  writing it.
- `updated_at` is application-managed; every mutation must update it in the same transaction.
- `last_used_at` should be coalesced rather than updated on every inference request.

The migration has not been applied to Railway, and the Worker still authenticates with bootstrap `SENKO_API_KEYS` until
the database access and API-key lifecycle milestones are implemented.
